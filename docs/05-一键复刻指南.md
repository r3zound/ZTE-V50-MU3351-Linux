# V50 刷 mu300-linux 一键复刻指南

> 目标：把 ZTE V50（`MU3351`）刷成 **Android + OpenWrt 双系统**，装完即可达到：
> **WiFi 热点可连且客户端能拿到 IP**、**USB 能上网**、**SSH / LuCI 可达**、**随时在两个系统间切换**。
>
> 面向：想复刻这套状态的其他人。
> 依据：本机 2026-10-09 ~ 10-10 的实测，每一步都有对应的验证命令。
>
> 参考文档：
> - `docs\01-可行性评估.md` —— 为什么 V50 可以刷（硬件等同 F50）
> - `docs\04-WiFi与DHCP根因分析.md` —— 三个会导致「连上却上不了网」的缺陷
> - `docs\06-OpenWrt操作手册.md` —— 刷完后的日常操作

## 0. 目标状态

刷完并做完第 4 步后，设备应达到：

| 能力 | 具体表现 | 验证方式 |
|---|---|---|
| WiFi 热点 | 广播 `<你的热点名>`，5GHz 信道 36 | 手机/PC 能扫到并关联 |
| **客户端拿 IP** | 关联后自动获得 `192.168.77.100-249` 段地址 | `ipconfig` 看是否 `192.168.77.x`（不是 `169.254.x`） |
| 上网 | 客户端经设备 4G 出网 | `ping 223.5.5.5` 通、能解析域名 |
| 管理 | SSH / LuCI 可达 | `ssh root@192.168.77.1`；`http://192.168.77.1/cgi-bin/luci/` |
| **USB 能上网** | USB 侧出现网卡并拿到 LAN 地址 | PC 见「Remote NDIS…」适配器，`192.168.77.247` |
| 双系统切换 | 从 Android 一键进 OpenWrt | `su -c mu300-linux` |
| 救砖通道 | 串口 root shell | COM12 115200 有 `root@mu300:~#` |

> ⚠️ **USB 与 WiFi 不要同时用**：两者在同一子网会产生重复路由，回包走 USB，
> 导致 WiFi 客户端连 ping 都不通。详见第 4.3 节。

## 1. 前置条件

```powershell
$adb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
```

| 项 | 要求 | 检查 |
|---|---|---|
| 机型 | ZTE V50（`MU3351`），板型 `ums9620_2h10_feimao` | `adb shell getprop ro.hardware` |
| 当前槽位 | **Android 必须在 `_a`**（安装器硬性要求） | `adb shell getprop ro.boot.slot_suffix` |
| Root | Magisk 已装，能拿到 uid=0 | `adb shell "/debug_ramdisk/su -c id"` |
| 空闲空间 | 分区后空闲区 ≥ 约 1 GiB（实测 32.4 GiB） | 跑安装器 `-Check` |
| 供电 | 全程供电稳定（刷机中掉电要靠 BROM 救） | —— |

**V50 的 root 入口与常见设备不同**：`su` **不在 PATH**，也没有 `/system/bin/su`；
真正的位置是 `/debug_ramdisk/su`（软链到 MagiskSU），而且**必须带 `-c`**
（不带会开交互 shell、读到空 stdin 后什么都没输出，看起来像 su 坏了）。

## 3. 打补丁 + 安装

### 3.1 打补丁（一次性，幂等）

```powershell
git clone https://github.com/dikeckaan/mu300-linux tools\mu300-linux
.\tools\apply-v50-patches.ps1
```

补丁脚本共 **12 步**，全部幂等（重跑 0 MISS），每步都写明了「为什么」：

| 步 | 修什么 | 不修的后果 |
|---|---|---|
| 1 | 机型识别认 `V50` / `MU3351` | 安装器拒绝继续 |
| 2 | 守住内核命令行 = `loglevel=5` | 加了别的东西 → **Android 侧再也切不进 Linux** |
| 2b | `switch.sh` 只比命令行前 10 字节 | 同上，且报错指向错误方向 |
| 3 | `mu300-hw` 的 bring-up 每步加超时 | 某步 hang 住 → 丢掉网络和登录 |
| 4 | `mu300-post` 只在 SSH 在听时才 re-arm | 坏启动被标记成好的，**设备再也回不了 Android** |
| 5 | 新增 `mu300-lancheck`（每次开机记录 LAN 关键状态） | 坏启动和好启动长得一样，无从排障 |
| 6 | `vendor-overlay.py` 支持打包 overlay | **改 `openwrt/overlay/` 完全不生效**（见 3.2） |
| 7 | 把改过的 OpenWrt 文件镜像进 `openwrt/vendor-extra/` | 同上 |
| 8 | 安装器探测可用的 `su`（`/debug_ramdisk/su`） | 报「su does not work」但 root 其实是好的 |
| 9 | **`mu300-hw` 去 BOM + 强制 UTF-8/LF** | 内核读不了 shebang，**WiFi 驱动永不加载** |
| 10 | **lan 防火墙上显式加 `br-lan`** | **客户端连上却拿不到 IP** |
| 11 | **`rndis0` 加入网桥后再清一次地址** | 用 RNDIS 时 WiFi 连 ping 都不通 |
| 12 | 编码硬门禁（UTF-16/BOM/CRLF 直接报错） | 把坏文件发到设备上才发现 |

> **3.2 为什么必须有第 6/7 步**：`install.ps1` 装的是**预编译 release 的 rootfs**，
> `openwrt/overlay/` 只在 `openwrt/build-rootfs.sh` 从源码构建时才被读取。
> 所以只改 overlay 树，对预编译安装**毫无影响**。
> 真正生效的通道是 `openwrt/vendor-extra/` → `tools/vendor-overlay.py` 打进
> `mu300-vendor-<os>.tar.gz` → `android-install.sh` 在 rootfs 之后**覆盖解包**。
>
> 另有致命细节：Windows 存不了 Unix 权限，打包时若一律写 0644，
> **init 脚本会丢掉可执行位，开机直接坏**。注入函数对
> `etc/init.d/`、`etc/uci-defaults/`、`etc/hotplug.d/`、`opt/mu300/bin/`、`lib/`、`usr/`
> 显式写 **0755**（补丁脚本已处理，可用 `tar -tvzf` 验证显示 `-rwxr-xr-x`）。

### 3.3 安装

```powershell
.\install.ps1 -Check                                  # 只读检查
.\install.ps1 -Lang zh -NoSelfUpdate -Answers <file>   # 正式安装
```

答案文件顺序（`tmp\answers-patched.txt` 是实测可用的一份）：

```
2        选 OpenWrt
2        面板版（openwrt-luci）
yes      机型不是 F50，继续
5        失败 5 次回 Android
yes      导入 Android 的热点名/密码
yes      包含 Mali GPU 文件
no       不要额外组件
1        内核 5.4（测试最久）
update   安装模式（保留已有配置）
<密码>   两遍 root 密码
INSTALL  确认
```

**成功标志**：输出 `MU300-INSTALL-OK`。
安装日志里应能看到注入生效：`8 entries from ...\openwrt\vendor-extra`。

> **别设 `MU300_USBNET`**：它按环境变量语义工作，写在命令行上没用，
> 而且会破坏 Android 侧对 Linux 镜像的识别（第 2 步）。USB 模式用第 4.3 节的正规做法。

### 3.4 装完立刻做：连上 WiFi

设备重启后进入 OpenWrt，热点 `<你的热点名>`，密码 `<你的热点密码>`。

## 4. 装机后设置（决定「能不能上网」的就是这几步）

### 4.1 确认 lan 防火墙区包含 `br-lan`（WiFi 拿 IP 的关键）

补丁第 10 步会通过 `90-mu300` 自动加上，但**必须复核**，因为这是最容易「看起来正常却全不通」的一项：

```sh
# 设备上（SSH 或串口）
uci -q get firewall.@zone[0].device          # 期望输出：br-lan
nft list chain inet fw4 input | grep br-lan  # 期望有一行 iifname "br-lan" jump input_lan
```

**为什么容易漏**：fw4 是从**网桥端口**推导某个区包含哪些接口的。
`br-lan` 声明为 `bridge_empty=1`（有线 LAN 不该等一个还不存在的成员），
而 `wlan0` 是 netifd 之后才加进网桥的 —— 等 fw4 渲染规则集那一刻，lan 区一个设备都没有：
input 链里没有 `br-lan` 的跳转，策略是 `drop`，**客户端发的包全被丢掉**。

此时的假象是：热点正常广播、wlan0 是 br-lan 的端口、br-lan 有 192.168.77.1/24、
dnsmasq 在 `0.0.0.0:67` 监听且 `dhcp-range` 正确、dropbear/uhttpd 都在听 ——
**只有渲染后的规则集能看出 lan 区其实是空的**。

若缺失，手工补（**`restart` 会因 flowtable 占用失败，必须 stop 再 start**）：

```sh
uci add_list firewall.@zone[0].device='br-lan'
uci commit firewall
/etc/init.d/firewall stop; sleep 3; /etc/init.d/firewall start
```

### 4.2 确认 `mu300-hw` 是纯 UTF-8、无 BOM

补丁第 9 步会处理，复核命令：

```sh
od -An -tx1 -N6 /etc/init.d/mu300-hw     # 必须是 23 21 2f（"#!/"）
```

若是 `ef bb bf`（UTF-8 BOM）或 `ff fe`（UTF-16LE），内核**无法解析 shebang、静默跳过该脚本**：
控制台没有任何报错，日志里也查不到，**WiFi 驱动永不 insmod**（无 `wlan0`、热点不广播），
而 dropbear/uhttpd 照常运行，让人以为一切正常。

上游仓库把这份文件提交成了 **UTF-16LE**，所以这条路必须走一遍。

### 4.3 设置 USB 网络模式（想要 USB 能上网就做）

**正规做法**（LuCI 面板 / ubus），**不是**改内核命令行：

```
http://192.168.77.1/cgi-bin/luci/admin/modem/device  →  USB 网络模式 → 选 RNDIS → 保存
```

等效命令：

```sh
ubus call mu300dash usb_set '{"kind":"net","value":"rndis","scope":"permanent","auto":"1"}'
ubus call mu300dash usb_get     # 复核 net_mode = rndis
```

它写的是所选系统的 `/etc/mu300/usb-net`；每次开机 `boot/init` 读它并在需要时重绑一次 gadget
（凭据写在 `/run/mu300/usb-net-applied`）。完整机制见
`docs\01-可行性评估.md` 的「USB 网络模式（RNDIS）的正确做法」一节。

**两点注意**：

1. **`update` 模式安装会覆盖 `etc/mu300/`**，所以每次整机安装后要重设一次。
2. **别和 WiFi 同时用**。两条链路在同一子网会让设备产生两条重复的
   `192.168.77.0/24` 路由，回包走 USB → WiFi 客户端能关联、能拿租约，却连 `ping br-lan` 都不通。
   根因是 `10-mu300-usb` 的清理顺序缺陷（补丁第 11 步已修），
   但**最省事的做法仍是只留一条链路**：用 USB 就断开 WiFi，或把 `usb-net` 设回 `ncm`。

### 4.4 日常用哪个通道

| 场景 | 用哪个 |
|---|---|
| 平时管理 | **WiFi + SSH**（补丁不管这个，需自己配免密，见下） |
| 网络坏了 | **USB 串口 COM12**（不受防火墙影响，唯一救命入口） |
| 系统切换 | **adb（Android 侧）** |

配 SSH 免密（一步到位）：

```powershell
.\tools\mu300.ps1 -Push "$env:USERPROFILE\.ssh\id_ed25519.pub" -To /tmp/k.pub
.\tools\mu300.ps1 -C "mkdir -p /etc/dropbear && cp /tmp/k.pub /etc/dropbear/authorized_keys && chmod 600 /etc/dropbear/authorized_keys && chmod 700 /etc/dropbear"
ssh -i $env:USERPROFILE\.ssh\id_ed25519 root@192.168.77.1
```

> **`scp` 不可用**：dropbear 没编译 `sftp-server`。传文件走 `tools\mu300.ps1 -Push/-Pull`
> （base64 + 设备自带的 `/opt/mu300/bin/busybox base64`；系统 busybox 没有 base64 applet）。

## 5. 验收清单

刷完后**逐条打勾**，任何一条不过就按第 4 节对应项处理。

```
□ 手机/PC 能扫到 <你的热点名>，能关联
□ 客户端拿到 192.168.77.100-249 的地址（不是 169.254.x）
□ 客户端 ping 192.168.77.1 通
□ 客户端能上网（ping 223.5.5.5 / 解析域名）
□ ssh root@192.168.77.1 能进
□ http://192.168.77.1/cgi-bin/luci/ 能打开（root / 密码）
□ od -An -tx1 -N6 /etc/init.d/mu300-hw  给出 23 21 2f
□ uci -q get firewall.@zone[0].device   给出 br-lan
□ ip route | grep -c 192.168.77         给出 1（不是 2）
□ 串口 COM12 115200 有 root@mu300:~#
□ （在 Android）su -c mu300-linux 能切回 OpenWrt
□ （用 USB 时）PC 出现 RNDIS 网卡并拿到 192.168.77.247
```

其中第 3 条（**路由只有 1 条**）是 4.3 节那个干扰问题的最简判据。

## 6. 常见故障 → 对应章节

| 症状 | 去这里 |
|---|---|
| 能关联，但拿不到 IP / ping 不通 | 4.1（fw4 的 lan 区为空） |

| WiFi 连 ping 都不通，USB 口却正常 | 4.3（两条重复路由） |

## 8. 附：配套的 UFI-TOOLS 插件

`V50插件开发\重启到OpenWrt插件.js` —— 在 **Android 侧的 UFI-TOOLS 管理界面**
（`192.168.0.1:2333`）加一个「重启到 OpenWrt」按钮，省掉每次开电脑敲 adb。

**安装**：UFI-TOOLS → 插件管理 → 导入这个 `.js` 文件 → 启用「高级功能」。

**它做什么**：
- 点按钮 → 弹窗自检（切换模块是否在、Linux 槽位是否就绪、`switch.sh status` 原文）
- 就绪才允许点「重启到 OpenWrt」，且需要**连点 5 次**确认（危险操作，会重启设备）
- 执行前先跑一次 `switch.sh --dry-run` 做完整校验，通过才真正写入
- 模块被停用时，额外给一个「启用切换模块」按钮（`disable` → `disable.off`，可逆）

**一次典型切换**：点按钮 → 看自检全绿 → 连点 5 次 → 数秒后设备重启进 OpenWrt。
