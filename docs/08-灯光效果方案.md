# V50 灯光效果方案（已实施并实测）

> 状态：**已实施，设备实测通过**（2026-10-10）。实施中发现了两个方案之外的问题，见第六节。
> 一句话：**无外网=红，有网+5GHz=白，有网+2.4GHz=蓝**；短按切频段（闪 2 下确认），长按 10 秒重启（三色轮流闪）。

---

## 一、灯语（按你的规格）

| 优先级 | 条件 | 颜色 | 实际写的通道 |
|---|---|---|---|
| **1（最高）** | **无外网**（数据未连接 / 无服务） | **红** | `sc27xx:red` |
| 2 | **有外网 + 热点 5 GHz** | **白** | `sc27xx:green` |
| 3 | **有外网 + 热点 2.4 GHz** | **蓝** | `sc27xx:blue` |

**为什么红优先**：三个状态里只有「没网」是需要人去处理的，所以它盖过频段显示。
即「无外网 + 2.4GHz」显示**红**，不显示蓝（已确认）。

### 这个配色为什么可靠

- **三个都是单通道纯色，完全不混色** → 亮度最高、最可靠，绕开「红+蓝做不出紫 / 太暗」的风险。
- **这三个颜色在 F50 上本来就是这么用的**（blue=4G 数据、white=5G 数据、red=无服务），**同一颗 PMIC**，
  属于上游已验证的用法。
- `sc27xx:green` 物理上是**白光**：ZTE Android 侧把它叫 `white`（同一个灯，不同名字），F50 用它表示 5G。

## 二、按键与重启

| 操作 | 灯光 |
|---|---|
| **短按**（切频段） | 立刻闪 2 下作为「已收到」反馈，随后变成新频段色（5G=白 / 2.4G=蓝） |
| **长按 10 秒**（重启） | **红 → 白 → 蓝 轮流闪**，一直闪到系统下电 |
| 重启完成后 | 自动回到「有网 + 5G = 白」 |

> 短按的闪 2 下是**先**发生的：切频段要 `wifi reload`，要好几秒，颜色是跟着新信道回来的，
> 不先闪一下，按键看起来就像没反应。
> 长按的三色闪复用 `mu300-led alarm`（上游 thermal-guard 用的就是这套），在 `reboot` **之前**起一个后台进程；
> `reboot` 是异步的，所以灯会一直闪到下电。

## 三、实现（三个脚本 + 一个配置文件）

| 文件 | 改了什么 |
|---|---|
| `rootfs/overlay/opt/mu300/bin/mu300-led` | 新增 `lit()`（按 `LED_LEVEL` 调亮度）、`render()`（**两状态算一颜色**，唯一的落色点）、`net()`；新增 `.net`/`.color` 状态文件；新增 `flash` 子命令；`data *` 走方案、`wifi *` 与 `wake`/`idle off`/`charge off`/`alarm off` 后补一次重绘 |
| `rootfs/overlay/opt/mu300/bin/mu300-wifi-band` | `set_band` 提交后**后台**跑一次 `mu300-led wifi sync 30` |
| `rootfs/overlay/opt/mu300/bin/mu300-buttons` | `KEY_FN short` 先 `mu300-led flash` 再切频段；`KEY_FN long` 在 `reboot` 前调 `mu300-led alarm on` |
| `openwrt/overlay/etc/uci-defaults/90-mu300` | V50 上生成 `/etc/mu300/led.conf`（**只在缺失时写**，用户校准不会被更新冲掉） |
| `openwrt/overlay/etc/init.d/mu300-buttons` | 补 `stop_service()`，见第六节 |
| `tools/apply-v50-patches.ps1` | 上面三个脚本进 vendor-extra 镜像清单；新增第 19 步门禁 |

### 为什么要一个 `render()`

颜色 = **f(有无网, 频段)**，两个输入，来自两条独立的流：
网络是 `mobile-data` 推来的事件，频段只能靠**查**（`iw dev wlan0 info` 的信道）得到，
而任何一条命令都只改其中一个。

沿用「每条命令各自点灯」的写法会出两个问题：
1. `data on` 和 `wifi on` 互相覆盖，谁后跑谁赢；
2. 切了频段之后**没人重算**，灯一直停在旧频段的颜色上。

`render()` 每次同时读两个状态再落色，任何一边变化都调它一次。
它内部走的是 `mu300-led` 本来就有的状态机（期望状态存 `/run/mu300/led/`，灯灭时的改动在下次 `wake` 补显示），
所以「灭灯期间切了频段，开机/唤醒后自动显示新颜色」是免费得到的，不是额外写的。

**`keyboard-backlight` 保持现状不动**：它按「热点是否起来」照旧亮（V50 上是 48/127），
本方案只接管那颗 RGB 指示灯。它是纯白光灯，做不出红/蓝。

### 「有外网」的判据

**调制解调器数据已连接**（`data on` / `data 5g`）——不做 ping 探测，不产生额外流量和延迟。
注意这**不等于真的能上外网**（DNS 坏、路由坏时它照样是白/蓝）。

## 四、可调参数（`/etc/mu300/led.conf`）

```
LED_TIMEOUT=0              # 0 = 常亮（F50 的默认值）
LED_SCHEME=v50             # classic（F50/U30 Air 原灯语，默认）| v50（本方案）
NO_NET_CHANNEL=sc27xx:red      # 无外网
NET5_CHANNEL=sc27xx:green     # 有网 + 5GHz → 白（这颗 PMIC 的 "green" 物理是白光）
NET24_CHANNEL=sc27xx:blue     # 有网 + 2.4GHz
KEY_FLASH_COUNT=2              # 短按后闪几下
#LED_LEVEL=100                 # 百分比，调暗某一路而不用重新编译
```

三个颜色参数不填时**默认取该设备本来就在用的那三路**（red/green/blue），
所以换一台设备只要把 `LED_SCHEME` 打开即可，不必重新量通道。
`LED_SCHEME` 不为 `v50` 时，上面所有新增逻辑都不执行 —— F50/U30 Air 的灯语**完全不受影响**（已回归实测）。

## 五、实测结果（2026-10-10，设备上逐条跑）

| # | 验证 | 方法 | 结果 |
|---|---|---|---|
| 1 | 有网 + 5 GHz = 白 | `mu300-led data on`，读 `/sys/class/leds/*/brightness` | `red=0 green=255 blue=0` ✅ |
| 2 | 有网 + 2.4 GHz = 蓝 | `mu300-wifi-band 2.4`，等 reload | `red=0 green=0 blue=255`，`iw` 显示信道 6 ✅ |
| 3 | 无网 = 红 | `data off` / `data error` | `red=255 green=0 blue=0` ✅ |
| 4 | 无网盖过频段 | 停在 2.4 GHz 上 `data error` | 仍是 `red=255` ✅ |
| 5 | 闪 2 下 | `mu300-led flash`，每 0.15 s 采样亮度 | `0 255 0 255 255 255…`，约 0.6 s 结束且**停在亮** ✅ |
| 6 | 颜色跟着频段自己走 | 切频段后不手工调任何灯 | 颜色自动变蓝，再切回自动变白 ✅ |
| 7 | 长按的三色闪 | `mu300-led alarm on`，采样三路 | `255/0/0 0/255/0 0/0/255 255/0/0 …` 轮流 ✅ |
| 8 | 闪完恢复正确颜色 | `alarm off` | 回到白 ✅ |
| 9 | classic 不回归 | 5 GHz + 有网 | `keyboard-backlight=48`，颜色 = 白 ✅ |
| 10 | 5 GHz 冷切换回归 | 5G→2.4G→5G 往返 | 5 GHz 正常起来（信道 36 / 80 MHz，`iw reg get` = US） ✅ |

另外在 PC 上用 `tools/led-scheme-test.sh`（假 sysroot，不需要设备）跑了 **18 条断言**，
覆盖本地化状态机，含 classic 回退与 `LED_LEVEL`。

> **颜色本身仍需用眼睛确认一次。** 上面测的是「哪一路被点亮、亮度多少」，
> 「`sc27xx:green` 在你眼前是不是白」这件事，只有你在机器旁才做得完（验收第 0 步）。
> 万一某一路偏暗或不是你想要的颜色：`led.conf` 里改 `LED_LEVEL` 调亮度，或改通道名换一路，都不用重新编译。

## 六、实施中发现并修掉的两个问题（方案之外）

### ① 设备的 `sleep` 不支持小数秒 —— 闪烁会慢 4 倍

`mu300-led` 里有个 `nap()`，原本是 `sleep "$1" 2>/dev/null || sleep 1`。
在这台设备上 OpenWrt 自带的 busybox 直接回 **`sleep: invalid number '0.05'`** 并退出，
于是所有小数都退化成整整 1 秒：

- 闪 2 下会变成 **2 × 2 秒 = 4 秒**（按键处理器被卡住 4 秒）；
- 上游 `siren`（thermal-guard 用的）每色 0.25 秒，实际会**按 1 秒走**——这是上游一直存在的问题，只是不显眼。

**修法**：`nap()` 优先问**发布版自带的 busybox**（`/opt/mu300/bin/busybox`，编译时带了 `FANCY_SLEEP`，
实测能吃小数），再退到系统 `sleep`，最后才退到整秒。顺带把上游 siren 的节奏也修对了。

### ② `/etc/init.d/mu300-buttons` 没有 `stop_service()` —— 按键被读两遍

`USE_PROCD=1` 的服务，`rc.common` 不会替 procd 实例做 stop，所以
**`/etc/init.d/mu300-buttons restart` 停不掉旧实例**。重启一次就有**两个 `mu300-keys` 同时读同一个 gpio-keys**，
于是**每次按键被处理两遍**：切频段切两次 = 没切，灯看起来毫无反应。

实测：重启前 1 套 → 重启后 2 套（pid 4852/4853 与 16768/16769）。

**修法**：给 init 脚本加 `stop_service()`，按名字在 `/proc/*/cmdline` 里找到并 kill。
（`mu300-keys` 是脚本的子进程、不是 procd 直接登记的那个，所以不能只 signal procd 实例。）
验证：连重启 4 次，每次都只剩 1 套。

> 写这个 `stop_service()` 时踩到一个竞态：进程在 glob 和读之间退出会让 shell 的**重定向**失败，
> `rc.common` 直接中断，表现为「restart 执行到一半就死了」。改用 `cat "$d/cmdline"` 取值即可
> （`cat` 缺文件只是普通错误，不会升级成 shell 级重定向错误）。

## 七、怎么在你的机器上验一次

```sh
# 0. 先用眼睛确认三色都能看见、亮度够（这是唯一需要人眼的一步）
mu300-led test

# 1. 有网 + 5GHz -> 应为白
mu300-led data on

# 2. 切到 2.4G -> 应变蓝（切频段会让 WiFi 断开几秒，属正常）
mu300-wifi-band 2.4

# 3. 想看当前到底点亮了哪一路（不用眼睛也能确认）
for c in red green blue; do echo -n "$c="; cat /sys/class/leds/sc27xx:$c/brightness; done
```

**断网验红**：`mu300-led data off`（红），`mu300-led data on`（恢复）。
**长按验重启闪烁**：真的长按 10 秒，红→白→蓝轮流闪到重启。

## 八、退路

| 情况 | 怎么退 |
|---|---|
| 想要 F50 原来的灯语 | `sed -i 's/^LED_SCHEME=v50/#LED_SCHEME=v50/' /etc/mu300/led.conf`（删掉那行也行），下一条 `data` 事件就回来了 |
| 某一路颜色不对 | 改 `led.conf` 里的通道名，或用 `LED_LEVEL` 调亮度，改完执行 `mu300-led data on` 即可 |
| 整个方案不想要 | 删掉 `/etc/mu300/led.conf`；`mu300-led` 回到 classic 分支，`mu300-buttons` 里那句 `mu300-led flash` 会因为 `v50` 不成立而自行空转（不报错） |
| 按键又变成「没反应」 | `ps w | grep mu300-keys` 看有几套；多于 1 就是第六节②那种情况，`/etc/init.d/mu300-buttons stop && … start`（现在 stop 会真的停干净） |

## 九、Android 侧（KANO 插件）对照

你那份「V50彩色灯控」插件控制的是 **Android 侧**通道，名字不同但**同一组灯**：

| 语义 | Android 侧 | Linux 侧 |
|---|---|---|
| 红 | `/sys/class/leds/red` | `sc27xx:red` |
| **白** | `/sys/class/leds/white` | `sc27xx:green` ← **同一颗，名字不同** |
| 蓝 | `/sys/class/leds/blue` | `sc27xx:blue` |
| 键盘背光 | （插件未暴露） | `keyboard-backlight`（本方案不动它） |

插件跑在 Android，**拿不到 Linux 的频段设置**，所以只能表达「最后一次已知状态」或干脆不表达。
→ 倾向：Android 侧**保持现状**（那是你在 Android 下的彩灯玩具），只统一颜色语言，不强行同步状态。
