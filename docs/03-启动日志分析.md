## 三、为什么你连不进去（推断，待现场验证）

> ⚠️ **本节的推断已被第七节推翻** —— 直接读设备配置后确认：`wlan0` **确实在** `br-lan` 里，
> WiFi/DHCP/Firewall 配置**全部正确**。保留本节是为了记录推理过程与排除项。

服务全在跑、`br-lan` 也有地址，那问题就在**客户端到 `br-lan` 的二层通路**上。

最可能的原因：**`wlan0` 虽然 UP，但没有真正加进 `br-lan`。**

理由链条：

1. `90-mu300` 里 br-lan 的端口只写了 USB：
   ```sh
   uci add_list network.$dev.ports='usb0'
   ```
   注释明说：「the MU300 LAN bridge carries the USB gadget (**Wi-Fi joins via wireless config**)」
   —— 也就是说，WiFi 要进网桥，**依赖 wireless 配置里的 `network='lan'` 被 netifd 正确应用**。

2. 但 WiFi 的启动顺序有个隐患：
   - `mu300-hw`（**START=12**）里 `hw_bringup` 调 `openwrt-wifi-config`（写 `/etc/config/wireless`）
     然后立刻 `wifi down; wifi up` 把 hostapd 拉起来
   - 而 netifd 是 **S20**，在这之后
   - `wifi up` 在 netifd 之前执行时，`wlan0` 可能**没有带着网桥成员关系启动**

3. `mu300-post` 里的 `wifiretry` 只处理「AP 没起来」的情况：
   ```sh
   ubus call hostapd.wlan0 get_status >/dev/null 2>&1 || { logger ... ; wifi up; }
   ```
   AP 已经在跑 → 不会触发 → **「AP 在跑但没进网桥」这个状态没人管**。

这与你观察到的现象完全吻合：

| 现象 | 用「wlan0 未进网桥」解释 |
|---|---|
| 热点能广播、能关联、握手成功 | hostapd 独立运行，AP 侧正常 ✓ |
| 拿不到 DHCP | 没有二层通路到 `br-lan`，dnsmasq 收不到请求 ✓ |
| 静态 IP 也 ping 不通 | 同上，二层就不通 ✓ |
| SSH/LuCI 连不上 | 同上 ✓ |

**注意：这是推断，不是结论。** 下一次刷机时用 USB（RNDIS）进去，跑
`brctl show` / `iw dev wlan0 info` 就能当场确认。

## 四、其他发现

### 1. `usb0 DOWN` —— USB 网络是断的

这意味着**即使当时装好了 NCM 驱动，USB 也走不通**。原因可能同上（`usb0` 进了 br-lan 但没被拉起来），
也可能是 gadget 在切换阶段被 OpenWrt 接管后没重新 up。

补丁里改成 **RNDIS** 后走的是 `rndis0`，而 `90-mu300` 对 `rndis0` 有单独的桥接钩子
（`hotplug.d/iface/10-mu300-usb`，K27），路径不同，值得一试。

### 2. 幽灵电池：`sc27xx-fgu` 报 75°C

```
sc27xx-fgu: init_cap = 621, ... Tbat = 750, ...
sc27xx-fgu: exceed temp range, sw ocv is invalid
```

`Tbat = 750` 即 75.0°C。V50 和 F50 一样**没有电池**，但 f50 配置仍加载了电量计模块，
于是它读到一个不存在的电池并持续报错。

这与文档记录的 F50 现象完全一致（FINDINGS：「a battery it does not have, at 75 °C」）。
**属于噪声，不影响功能** —— 但要留意：`mu300-toolkit` 或面板里若显示电池信息会是假的。

### 3. `dnsmasq` 启动很晚（PID 12834）

其它服务 PID 在 3000–5000，`dnsmasq` 是 12834 —— 说明它**启动得晚得多**，很可能是
netifd 配置完 LAN 之后才起来的（或重启过）。

**这解释了「连上热点但等不到 IP」的另一半原因**：即使二层是通的，
在你尝试的那段时间里 DHCP 服务可能还没就绪。

### 4. 固定 TTL 与热控等

日志里没有发现致命错误。`sprd-wlan` 有大量 `CMD_SET_IE` / `loopcheck` 噪声输出，
把 `logread` 的环形缓冲冲掉了，导致看不到用户态服务的启动记录 —— 这也是为什么
之前 grep `dropbear|dnsmasq` 在 logread 里一无所获。

## 八、一个必须知道的坑：`openwrt/overlay/` 对预编译安装**不生效**

这是本次发现的**最重要的工程问题**。

`install.ps1` 安装时下载的是**预编译的 rootfs 包**（`mu300-openwrt-luci-rootfs.tar.gz`），
只额外叠加 `tools/vendor-overlay.py` 生成的厂商文件包。
`openwrt/overlay/` **只在从源码构建镜像时（`openwrt/build-rootfs.sh`）才被读取**。

**所以对 `openwrt/overlay/` 的修改，在预编译安装里完全不会生效。**

### 解决：走 vendor 覆盖包注入

`tools/android-install.sh` 第 269-277 行的解包顺序是关键：

```sh
tar -xzpf $tarball -C $M/$os.new                        # ① 预编译 rootfs
if [ -f $T/mu300-vendor-$os.tar.gz ]; then
    tar -xzpf $T/mu300-vendor-$os.tar.gz -C $M/$os.new  # ② 厂商覆盖包 —— 在①之后，会覆盖①
fi
```

**厂商覆盖包在 rootfs 之后解压，所以它的文件会生效。**

补丁脚本因此做两件事：

1. 给 `tools/vendor-overlay.py` 加 `add_overlay_tree()`，并把 `openwrt/vendor-extra/` 打进覆盖包
2. 把每个被补丁修改过的文件**镜像**到 `openwrt/vendor-extra/`（保持 rootfs 相对路径）

**并且必须处理权限位**：Windows 存不了 Unix 权限，`add_tree` 会把所有文件写成 `0644`
—— 那样 init 脚本就没有可执行位，开机直接坏掉。所以注入函数对
`etc/init.d/`、`opt/mu300/bin/`、`lib/`、`usr/` 等路径显式写 `0755`。

**已验证**（用真实数据生成覆盖包后 `tar -tvzf`）：

```
-rwxr-xr-x  0 root root  3483  etc/init.d/mu300-hw
-rwxr-xr-x  0 root root  3824  etc/init.d/mu300-post
-rwxr-xr-x  0 root root  2426  opt/mu300/bin/mu300-lancheck
```

### 受影响的补丁

| 补丁 | 原来的状态 | 现在的状态 |
|---|---|---|
| 1 机型识别 | ✅ 有效（安装器自身读） | ✅ |
| 2 RNDIS | ✅ 有效（boot 镜像本地构建） | ✅ |
| 3 WiFi 超时防护 | ❌ **原本无效** | ✅ 经注入生效 |
| 4 re-arm 修复 | ❌ **原本无效** | ✅ 经注入生效 |
| 5 LAN 自检 | — | ✅ 经注入生效 |

### 踩到的两个操作细节（已修）

1. **`update/wipe` 那一步要的是文字 `update`，不是数字 `1`。** 给数字会报「无效的选择」，
   答案文件整条错位。
2. **检查完配置后必须卸载挂载的 Linux 区**，否则安装器报 `ALREADY-MOUNTED loop32` 直接失败。
   卸载：`sh /data/local/tmp/am.sh -u /data/local/tmp/lx`

### 没达到的部分

**1. RNDIS 没有生效 —— USB 仍枚举成 `CDC NCM`。**

boot 镜像里的内核命令行**确认写入了** `loglevel=5 MU300_USBNET=rndis`（读 boot header 第 44 字节验证），
但设备起来的 gadget 仍是 NCM。

上游文档其实早写明这条路径**从未被测过**：

> FINDINGS §35 **K6**（RNDIS in one configuration）: **not measured, no Windows host**; kept

以及 `boot/init` 的注释提到更早的 RNDIS+NCM 组合「bound the whole device to usbser and showed
no network adapter」。

**结论：RNDIS 是上游未验证的路径，实际不生效。** USB 侧要继续用，只能回到 NCM
（而 NCM 在这台 Windows 上缺 catalog 签名装不了驱动）。
**所以 USB 不是可靠通道，WiFi 是唯一出路。**

**2. 这次开机的热点没有广播。**

设备在 Linux 里（USB gadget 在），但 AP 未出现、无 RNDIS 网卡、SSH 不可达 ——
与之前某次「卡得比较早」的现象同类。因此 **WiFi 还无法实测验证**。
