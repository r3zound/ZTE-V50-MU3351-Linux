### 1.2 默认启动语义 —— 这次和旧版不一样

**实测（`mu300-next-boot status`）：**

```
default boot: linux
locked: yes (Android only by hand)
failed boots in a row before Android: 5 (only while a new boot image is on trial)
boots since the last good one: 0
```

对应三个文件/状态：

| 位置 | 值 | 说明 |
|---|---|---|
| `/etc/mu300/default-boot` | `linux` | 默认启动项 |
| `/mnt/mu300-disk/.mu300/boot-lock` | 存在 | 已锁定，LK 永不回退 |
| `/mnt/mu300-disk/.mu300/boot-attempts` | `5` | 连续失败次数上限 |

> ⚠️ **`boot-attempts` 不在 `/etc/mu300/` 下**。它在**Linux 磁盘分区**的 `.mu300/boot-attempts`
> （上游 `boot/init` 读的是 `"$2/.mu300/boot-attempts"`，`$2` 是磁盘目录）。读不到时上游默认就是 5
> （`case $max in [1-6]) ;; *) max=5 ;; esac`）。

**关键点：旧版上游的语义是「进 Linux 必然回 Android」（一次性试用），现在不是了。**
锁定之后，只有**手动** `mu300-next-boot android` 才会回 Android；连续 5 次启动失败才自动回退，
而且那句括注说得很清楚：**只在「新启动镜像处于试用状态」时才自动回退**。

详见 §11。

## 2. 上游 v2026.10.23.2 **已经原生支持 V50**

**这是本次改写的核心：上游自己已经把 V50 做了，不需要我们再移植一遍。**

上游源码核对（`mu300-linux-src-v2026.10.23.2.tar.gz`，顶层目录 `mu300-linux-2026.10.23.2/`）：

| 上游文件 | 作用 |
|---|---|
| `rootfs/overlay/opt/mu300/lib/v50-card.sh` | V50 四种板型的 SIM 映射 |
| `upstream/port/drivers/leds/leds-aw9523b.c` | **内核态** AW9523B 面板彩灯驱动（主线 `drivers/leds/`） |
| `upstream/port/drivers/misc/zte-v50-sim.c` | V50 SIM 复用（mux） |
| `upstream/patches/0017-mmc-sdhci-sprd-V50-eMMC-host-kept-awake.patch` | V50 eMMC 保持唤醒 |
| `tests/test_v50_sim.py` | SIM 映射测试 |
| `rootfs/overlay/opt/mu300/bin/mu300-device` 里的 `v50_dt()` / `v50_fix()` | 靠设备树认出 V50 |
| `rootfs/overlay/opt/mu300/bin/mu300-led` 里的 `v50:` 灯语 | 面板灯的配色 |

### 2.1 SIM 映射（上游 `v50-card.sh`）

四种板型由 `board_id` 决定（读 `/proc/driver/board_id`，主线内核没有 `androidboot.*` 时
再读设备树 `chosen/bootargs` 里的 `androidboot.zte_boardid`），取值 **0–3**：

| card | 物理卡 | slot（modem 的 SIM 接口） | 开关 | 电平 |
|---|---|---|---|---|
| 0 | 内置 SIM 1 | 0 | `psim_select` | 0 |
| 1 | 内置 SIM 2 | 1 | `chip_select` | 0 |
| 2 | 内置 SIM 3 | 1 | `chip_select` | 1 |
| 3 | 外置 SIM | 0 | `psim_select` | 1 |

各板型有的卡：`board_id=0` → `0 1 2`；`1` → `0 1 2 3`；`2` → `0 1 3`；`3` → `0 1`。

### 2.2 设备识别：标签写错也能认对

上游 `mu300-device` 的 `v50_dt()` 只看设备树里有没有
`soc/*/i2c@2270000/aw9523b_led@5b` 这个节点；`v50_fix()` 据此纠正机型标签。

> **实测**：本机 `/opt/mu300/bin/mu300-device` 输出 `v50` ✅

### 2.3 面板彩灯：已经是内核驱动，不是用户态 I²C

上游 `mu300-led` 里已经写好了 v50 的灯语：

```
v50)  POWER=  DATA=v50:$V50_NET:blue  DATA5G=v50:$V50_NET:white
      NODATA=v50:$V50_NET:red  WIFI5=v50:wifi:white  WIFI24=v50:wifi:blue
```

其中 `$V50_NET` 随当前 SIM 槽在 `net2`/`net1` 之间切换。写灯走的是
**`/sys/class/leds/<名字>/brightness`**——也就是内核 LED class。

> **实测**（7.3 内核上）：
> `/sys/class/leds/` 里同时有 `aw9523b:pin0` … `aw9523b:pin15`、
> `v50:net1:{blue,red,white}`、`v50:net2:{blue,red,white}`、`v50:wifi:{blue,red,white}`。
> `find /lib/modules -name '*aw9523*'` **没有结果** —— 说明 `leds-aw9523b` 是**直接编进 7.3 内核**的，
> 不是可加载模块。上游的 `mu300-led` 用的正是这些名字，两边对得上。

**所以：6.18 时代那套「用户态直控 AW9523B 的 I²C + 掩码」方案不再需要了。**
（设备上 `/etc/mu300/led.conf` 里还留着 `LED_BACKEND=i2c` / `LED_I2C_*` / `LED_AW_*` 几行，
但设备上的 `mu300-led` 里 **0 处**引用这些键 —— **已经是死配置**，留着无害。）

### 2.4 安装器也已经认 V50

上游 `install.sh` / `install.ps1` 里：

* 认机型：model `V50 / MU3351` + platform `ums9620`（三项不全就拒绝，不问）。
* **V50 只允许主线内核**：选 5.4 会被拒（`The ZTE V50 runs a mainline kernel only (6.18, 7.2 or 7.3)`），
  V50 的默认选项是 **2（6.18）**。
* **V50 不允许从源码构建**：`The ZTE V50 runs a mainline kernel only: install a prebuilt release (without --build)`。
* 上游给 V50 分配的 USB 网络地址是 **192.168.79.1**（见 §1.3 的说明）。

## 3. 我们相对上游 v2026.10.23.2 实际只补了三处

补丁统计（`patches/v50-changes-vs-upstream-v2026.10.23.2.patch`）：

| 项 | 数值 |
|---|---|
| 文件大小 | 197,534 字节 |
| diff 条目 | **28**（= **14 改** + **14 增** + **0 删**） |

这 28 个条目里绝大多数是**同一处改动在树里的多个副本**（`openwrt/overlay/…` 与
`openwrt/vendor-extra/…` 各一份）。**真正属于「上游没有、我们补」的只有 3 处：**

### 3.1 `mu300-led flash` —— 按键的「我听到了」回执

上游 `mu300-led` 的子命令只有 `alarm`（过热警报）/ `siren` / `test` / `events` 等，**没有 `flash`**。

**为什么必须加**：短按切频段要跑 `wifi reload`，颜色要等新信道回来才变。
不先闪一下，按键**看起来像没反应**。

```sh
# 闪几下由 led.conf 决定
KEY_FLASH_COUNT=$(sed -n 's/^LED_KEY_FLASH_COUNT=\([0-9][0-9]*\)$/\1/p' "${MU300_LED_CONF:-/etc/mu300/led.conf}" 2>/dev/null | tail -n1)
case $KEY_FLASH_COUNT in ''|*[!0-9]*) KEY_FLASH_COUNT=2 ;; esac
```

`flash` 复用**当前正在亮的那一路**（无服务=红 / 有网+5G=白 / 有网+2.4G=蓝）闪 `KEY_FLASH_COUNT` 次；
设备本来是暗的就不闪（暗就是暗，闪一下不该把本该睡着的设备点亮）。

> **实测**：设备 `/etc/mu300/led.conf` 里 `KEY_FLASH_COUNT=2`；
> `mu300-buttons` 里 `"$KEY_FN short") mu300-led flash; …` —— 按键已接上。

### 3.2 `mu300-buttons` 认 V50 的键码 `KEY_FN=464`

上游只认 `KEY_POWER=116` / `KEY_WIFI=138`（U30 Air 的键），**V50 一个都不报**，
所以在补上之前按键完全没反应。我们补了 `KEY_FN=464`（V50 唯一的实体键，`key-function` 节点）
并实现长按 10 秒重启。详见 §7。

### 3.3 `/etc/init.d/mu300-buttons` 补 `stop_service()`

**上游这个脚本没有 `stop_service()`**（只有 `start_service()`）。后果：`restart` 停不掉旧实例，
第二个 `mu300-keys` 会**同时读同一个 gpio-keys**，
于是**每次按键被处理两遍** —— 切频段切两次等于没切。

补丁补上 `stop_service()`（按 `/proc/*/cmdline` 匹配 `mu300-keys` / `mu300-buttons` 杀掉整组）。

> **实测**：现在设备上 `mu300-keys` 进程**只有 1 个**：
> `mu300-keys -l 10000 -t 5` ✅（`-l 10000` 说明长按阈值走的是 V50 分支，见 §7）。

## 5. 内核可选 5.4 / 6.18 / 7.2 / 7.3 —— 上游本来就有这个选择

**结论先说：安装向导早就在问，不需要「添加」。** 之前以为没有，是因为答案文件把它答成了 5.4。

| 位置 | 行为 |
|---|---|
| `install.ps1:1784` | **无条件**问 `Which kernel?`（1=5.4 / 2=6.18 / 3=7.2 / **4=7.3**） |
| `install.sh:834` | 仅在 `MODE=prebuilt` 且不是从包安装时问 |

> 旧文档写的是 `install.ps1:694` / `install.sh:393`（v2026.10.12 的行号）。
> v2026.10.23.2 的上游脚本长了不少，行号已变成上表这两个。
> **7.3 这个选项在 v2026.10.23.2 里确实存在**（上游原文：`4) 7.3  the newest mainline Linux (7.3 for now)`），
> 不是「以本机向导为准」的猜测。
> 另外：选 5.4 时若机型是 V50，上游会直接拒（V50 只跑主线内核）。

已装好的设备不用重装，可以就地切换：

```sh
mu300-update kernel            # 看当前
mu300-update kernel 7.3        # 切（会重写 boot_b 并提示重启）
mu300-update rollback-boot     # 后悔药：用设备上保留的 prev.* 还原，不需要网络
```

> **实测**：设备上 `mu300-update kernel` → `kernel: 7.3 (running 7.3.0)` ✅

`mu300-update kernel` 的机制：下载 `mu300-kernel-<版本>.tar.gz` → 把模块装进已装系统的
`lib/modules/<release>/` → 组装新启动镜像 → **先把当前镜像存成 `prev.body` / `prev.vbmeta` /
`prev.footer` / `prev.kernel` 再写** → 校验写入。各版本的模块**并存**，随时能切回。

### ⚠️ 两个坑

**① 设备连不上 GitHub。** 实测 `wget github.com` 返回
`Failed to send request: Operation not permitted`（IPv4/IPv6 都一样；同期清华镜像正常）。
所以 `mu300-update` 在设备上**没法自己下载**。绕法是用它留的后门：

```sh
MU300_KERNEL_BUNDLE=/mnt/mu300-disk/mu300-kernel-7.3.tar.gz \
MU300_RELEASE=v2026.10.23.2 mu300-update kernel 7.3
```

包在 PC 上下载并**对照官方 `SHA256SUMS` 校验**后推给设备（设备端再核一次 sha256）：

```powershell
$base='https://github.com/dikeckaan/mu300-linux/releases/download/v2026.10.23.2'
Invoke-WebRequest "$base/mu300-kernel-7.3.tar.gz" -OutFile $f
(Get-FileHash $f -Algorithm SHA256).Hash.ToLower()   # 与 SHA256SUMS 里的比对
```

**② 不要跑 `mu300-update apply`（整包更新）。** 它的保留清单只有
`etc/config`、`etc/mu300`、`etc/dropbear`、`root`，**本仓库的全部补丁都不在里面**——
`mu300-hw`、`distfeeds.list`、`dashboard-info`、`home.js`、`mu300-buttons` 会被 upstream 版本覆盖
（而 upstream 的 `mu300-hw` 在 6.18 时代还是 UTF-16，会直接让 WiFi 驱动不加载；
**在 v2026.10.23.2 上它已经是 UTF-8，但其余覆盖问题依旧**）。**只做 `kernel` 这一步。**

## 6. 5GHz 起不来 —— 根因是监管域，不是时序

### 症状

5GHz 配置下 hostapd 直接失败，**设备上没有任何地方报错**：

```
hostapd: wlan0: interface state UNINITIALIZED->COUNTRY_UPDATE
hostapd: Frequency 5180 (primary) not allowed for AP mode, flags: 0x40853 NO-IR
hostapd: Primary frequency not allowed
hostapd: Could not select hw_mode and channel. (-3)
hostapd: wlan0: interface state COUNTRY_UPDATE->DISABLED
hostapd: wlan0: AP-DISABLED
```

### 根因链

```
cfg80211 在 rootfs 挂载前就请求 regulatory.db —— 必然失败
   [2.19s] cfg80211: failed to load regulatory.db
→ cfg80211 停留在世界域 country 00
→ 世界域里 5GHz 全部标记 NO-IR（禁止主动发射）
→ hostapd 不能在该信道起 AP
```

**关键实验**（在同一台设备上）：

```
手动跑 regdb-load 之前： iw reg set TR  → 仍是 country 00      （改不动）
手动跑 regdb-load 之后： iw reg set TR  → country TR: DFS-ETSI  （立刻生效）
                        iw reg set US  → country US: DFS-FCC
                        iw reg set BO  → country BO: DFS-JP
```

所以 `regdb-load`（上游自带，`opt/mu300/bin/regdb-load`）才是关键：它把
`/lib/firmware/regulatory.db` 通过 `/sys/class/firmware` 喂给挂起的固件请求，再 `iw reg reload`。
**开机那次没成功**，于是国家码形同虚设。

### 修法

`mu300-lancheck`（每次开机跑一次）现在**先补喂 `regdb-load`，再修无线**——顺序重要，必须在重启
无线之前，hostapd 才能读到国家码。然后它按 **`operstate` + 是否在网桥里** 判断，不满足就
`wifi down; sleep 3; wifi up`，最多 3 轮。

> 上游 `mu300-hw` 里其实也调了一次 `regdb-load`（在 netifd 之前），并在 netifd 起 hostapd 前
> 套用国家码。**我们的 `mu300-lancheck` 在 netifd 之后再补喂一次** —— 因为第一次的加载发生在
> rootfs 还没完全就绪的时候，而 hostapd 是 netifd 才拉起来的。

**冷启动实测（7.3.0，2026-10-25 这次启动的 `/tmp/mu300-lancheck.log`）：**

```
26.17 wlan0 not serving (exists=yes operstate=down bridge-port=1): wifi down; wifi up (attempt 1)
49.62 br-lan=[192.168.77.1/24 ] ports=[rndis0 wlan0 ] wlan0=up dnsmasq=[10732 ] tcp22=1 tcp80=1 udp67=0 fw-jump=1 range=[dhcp-range=set:lan,192.168.77.100,192.168.77.249,255.255.255.0,12h;]
```

> 6.18 时代同一段日志长得几乎一样（历史记录）：
> `36.79 wlan0 not serving (exists=yes operstate=down bridge-port=1): wifi down; wifi up (attempt 1)`
> → `59.87 br-lan=[192.168.77.1/24] ports=[rndis0 wlan0] wlan0=up range=[dhcp-range=...]`

**两个曾经写错的地方，都值得记一下**：

1. 原来的判断只看「wlan0 是不是网桥端口」。6.18 上 wlan0 **一直在网桥里**，是**射频**起不来，
   所以条件从不触发、日志看着像通过。**判据必须是 `operstate`。**
   > 7.3 上同样如此：日志里 `bridge-port=1` 但 `operstate=down` —— 网桥成员身份和射频可用是两回事。
2. 第一版修复用 `if [ -d /sys/class/net/wlan0 ]` 守卫整块。但 lancheck 跑的时候 `br-lan` 刚拿到
   地址、**wlan0 还不存在**（lan 接口先于无线接口起来），于是整块被跳过——**在它本该生效的那个场景
   里恰好失效**。必须先等 wlan0 出现（最多 60s）。

## 7. 实体按键：短按切 2.4/5GHz，长按 10 秒重启

### V50 的键码和上游**完全对不上**

上游 `mu300-buttons` 只认 `KEY_POWER=116` 和 `KEY_WIFI=138`（U30 Air 的键）。V50 一个都不报，
所以**按键此前什么都不做**。实测（`/dev/input/event0` 解码）：

| 设备树节点 | `linux,code` | 十进制 | 上游期望 | 说明 |
|---|---|---|---|---|
| `key-power` | `0xBE` | **190** | `KEY_POWER=116` ❌ | KEY_F20 |
| `key-volumedown` | `0x72` | 114 | — | |
| `key-volumeup` | `0x73` | 115 | — | |
| **`key-function`** | `0x1D0` | **464** | `KEY_WIFI=138` ❌ | **KEY_FN，V50 唯一的实体键** |

> 抓取方法：`dd if=/dev/input/event0 bs=24 count=1 | hexdump`，按 `input_event` 结构解
> （64 位下 24 字节：tv_sec 8 + tv_usec 8 + type 2 + code 2 + value 4；`EV_KEY=1`，
> value 1=按下 / 0=释放）。设备上没有 `od`，但有 `hexdump`。
>
> **上游源码核对**：v2026.10.23.2 的 `mu300-buttons` 里**仍然只有** `KEY_POWER=116` 和
> `KEY_WIFI=138`，**没有 `KEY_FN`**。所以 §3.2 的补丁到新版本上**依然必要**。

### 改动（`mu300-buttons`）

```sh
KEY_FN=464                      # 新增

# 长按阈值按设备树判断，不按机型：V50 与 F50 的模型字符串相同（DEVICE=f50），
# 但 key-function 这个节点只有 V50 有
HOLD=${MU300_BUTTONS_HOLD:-$([ -d /proc/device-tree/gpio-keys/key-function ] && echo 10000 || echo 3000)}

mu300-keys -l "$HOLD" -t 5      # 原为写死的 -l 3000

case "$code $kind" in
    ...
    "$KEY_FN short") mu300-led flash; [ "$was_idle" = 1 ] || in_background "$DEADLINE" band_toggle ;;
    "$KEY_FN long")
        logger -t mu300-buttons "V50 key held ${HOLD} ms: rebooting"
        mkdir -p "$PST"; : > "$PST/reboot"
        if is_openwrt; then reboot; else systemctl reboot; fi ;;
esac
```

频段切换直接复用上游的 `mu300-wifi-band toggle`（2g/ch6/HT20 ↔ 5g/ch36/VHT80 + `wifi reload`）。

**实测（6.18 时代，2026-10-10）**：短按 → `band` 从 `2g ch=6` 变 `5g ch=36` ✅；
长按 10 秒 → `uptime` 归零、重启 ✅。

> **实测（7.3，2026-10-25）**：
> 设备上 `/proc/device-tree/gpio-keys/key-function` **存在** →
> `mu300-keys` 实际命令行是 **`-l 10000`**（长按 10 秒）✅，
> 且 **`mu300-keys` 只有 1 个实例**（§3.3 的 `stop_service()` 生效）✅。
> 短按/长按的**动作本身本次未在 7.3 上复测**（那需要人按实体键），沿用 6.18 的实测结论。

> 一个容易误判的点：上游逻辑里「设备处于 idle 时，第一次按下只唤醒、不执行动作」
> （`was_idle`）。所以按键"没反应"时先看 `/run/mu300/power/state` 是否为 `active`、
> `/run/mu300/led/.idle` 是否存在、`mu300-power daemon` 是否在跑——**再**去怀疑键码。

## 8. 无线国家码：选 US（实测功率最高）

`iw reg get` 实测的 EIRP 上限：

| 国家 | 2.4GHz | 5GHz 低段 | 5GHz 高段 |
|---|---|---|---|
| `BO` | 20 dBm | 30（DFS） | 30 |
| **`US`** | **30 dBm** | 23（**允许 AP**） | **30** |
| `CN` | 20 dBm | 23（NO-OUTDOOR） | **33** |
| `TR` / `DE` | 20 dBm | 23 | — |
| `JP` | 20 dBm | 20 | — |

**选 `US`**：2.4GHz 上限 30 dBm，是 BO/CN（20）的 1.5 倍——而 2.4GHz 是唯一在任何监管状态下都能起
AP 的频段；而且 US 允许在低段 5GHz 起 AP（BO 不允许）。

> `CN` 的 33 dBm 只出现在 5.8GHz 段（5725–5850），2.4GHz 仍是 20。
> 注：硬件有自己的发射上限，这几行只是**监管天花板**。

改国家码：`uci set wireless.radio0.country='DE'; uci commit wireless; wifi reload`

> **实测（7.3，2026-10-25）**：`iw reg get` → `country US: DFS-FCC`，
> 其中 2400–2472 @ 40MHz / 30 dBm、5150–5250 @ 80MHz / 23 dBm —— 与上表一致 ✅。
> 设备配置：`wireless.radio0.country='US'`、`band='5g'`、`channel='36'`、`htmode='VHT80'`。

## 10. 顺带修掉的顺序 bug：vendor-extra 镜像早了

`apply-v50-patches.ps1` 的镜像步骤（第 7 步）**原本跑在第 10/12/13/16 步之前**，而这几步都会继续改
`openwrt/overlay/` 里的文件。后果：

> 单次干净运行产出的 `openwrt/vendor-extra/` 是**改动前**的内容。
> 而**预编译安装只读 vendor-extra、不读 `openwrt/overlay/`**（那棵树只在 `build-rootfs.sh` 从源码
> 构建时才用）——所以那样的设备会拿到未修补的 `90-mu300` / `10-mu300-usb` / `dashboard-info`，
> 而本仓库看上去是打过补丁的。

重复运行会掩盖它（每次拷贝的是上一次的成品，差一轮）。已改成函数 `Mirror-VendorExtras`，
在第 17b 步（所有内容修改之后、编码门禁之前）调用。

**同类盲区**：`mu300-buttons` 只在 `rootfs/overlay/` 里（`build-rootfs.sh` 把它挂到
`/in/opt-mu300` 再拷进 `/opt/mu300`），**原先不在 vendor-extra 镜像列表里**，同样会漏。
已加入：`opt\mu300\bin\mu300-buttons=rootfs\overlay\opt\mu300\bin\mu300-buttons`。

> 补丁里 28 个 diff 条目里有 14 个是 `openwrt/vendor-extra/…` 的副本 —— 就是这么来的。

## 11. 双启动竞态：上游已经修了

上游 v2026.10.23.2 的 `mu300-next-boot` 从 6.1 KB 量级长到 **12,793 字节（≈12.8 KB）**，
`boot/init` 从 41 KB 量级长到 **56,499 字节（≈56.5 KB）**（上游源码核对）。

新增的能力：

| 能力 | 作用 |
|---|---|
| `lock` / `unlock` | Linux 侧置 `successful=1`，**LK 永不回退**（回 Android 只能手动） |
| `--trial` | 新启动镜像的第一次启动：解锁、限定次数，之后再锁上 |
| `flock` | 串行化写 misc（`command -v flock` 有就用，没有就跳过） |
| `set_conf` | 原子写（先写临时文件再 `mv`，不会留下空文件） |

上游注释里写明的竞态：`--rearm` 与「Switch to Android」互相覆盖。

> ⚠️ **`boot/init` 必须与 `mu300-next-boot` 成对升级** —— 新版 `boot/init` 靠 misc 里的
> `successful` 位判断要不要回退，两个文件版本对不上会误判。

> ⚠️ **`android` 子命令仍是永久语义**：回 Android 后**不会自己回来**。
> 想长期留在 Linux 应用，要跑 **`mu300-next-boot lock`**，而不是只跑一次 `linux`。

> **本项目给 `mu300-post` 加的「等 SSH 可达才 `--rearm`」上游没有** ——
> 上游就是 `sleep 30; exec /opt/mu300/bin/mu300-next-boot --rearm`（源码核对确认）。
> 这条改动仍然必要（§4）。

## 13. 别忘了
