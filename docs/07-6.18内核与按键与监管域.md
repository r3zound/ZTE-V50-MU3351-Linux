# V50：6.18 主线内核、实体按键、监管域与默认设置

2026-10-10 实测记录。这份文档对应补丁第 15（无线修复）、16（主机名/时区/国家码）步和
`mu300-buttons` 的改动。

## 1. 内核可选 6.18 / 7.2 —— 上游本来就有这个选择

**结论先说：安装向导早就在问，不需要"添加"。** 之前以为没有，是因为答案文件把它答成了 5.4。

| 位置 | 行为 |
|---|---|
| `install.ps1:694` | **无条件**问 `Which kernel?`（1=5.4 / 2=6.18 / 3=7.2） |
| `install.sh:393` | 仅在 `MODE=prebuilt` 时问 |

`tmp\answers-patched.txt` 的第 8 项是内核选择，填的是 `1`，也就是 5.4 —— 所以设备一直是 5.4。

已装好的设备不用重装，可以就地切换：

```sh
mu300-update kernel            # 看当前
mu300-update kernel 6.18       # 切（会重写 boot_b 并提示重启）
mu300-update rollback-boot     # 后悔药：用设备上保留的 prev.* 还原，不需要网络
```

`mu300-update kernel` 的机制：下载 `mu300-kernel-<版本>.tar.gz` → 把模块装进已装系统的
`lib/modules/<release>/` → 组装新启动镜像 → **先把当前镜像存成 `prev.body` / `prev.vbmeta` /
`prev.footer` / `prev.kernel` 再写** → 校验写入。5.4 与 6.18 的模块**并存**，随时能切回。

### ⚠️ 两个坑

**① 设备连不上 GitHub。** 实测 `wget github.com` 返回
`Failed to send request: Operation not permitted`（IPv4/IPv6 都一样；同期清华镜像正常）。
所以 `mu300-update` 在设备上**没法自己下载**。绕法是用它留的后门：

```sh
MU300_KERNEL_BUNDLE=/mnt/mu300-disk/mu300-kernel-6.18.tar.gz \
MU300_RELEASE=v2026.10.16 mu300-update kernel 6.18
```

包在 PC 上下载并**对照官方 `SHA256SUMS` 校验**后推给设备（设备端再核一次 sha256）：

```powershell
$base='https://github.com/dikeckaan/mu300-linux/releases/download/v2026.10.16'
Invoke-WebRequest "$base/mu300-kernel-6.18.tar.gz" -OutFile $f
(Get-FileHash $f -Algorithm SHA256).Hash.ToLower()   # 与 SHA256SUMS 里的比对
```

**② 不要跑 `mu300-update apply`（整包更新）。** 它的保留清单只有
`etc/config`、`etc/mu300`、`etc/dropbear`、`root`，**本仓库的全部补丁都不在里面**——
`mu300-hw`、`distfeeds.list`、`dashboard-info`、`home.js`、`mu300-buttons` 会被 upstream 版本覆盖
（而 upstream 的 `mu300-hw` 还是 UTF-16，会直接让 WiFi 驱动不加载）。**只做 `kernel` 这一步。**

### 6.18 实测结果

| 项 | 结果 |
|---|---|
| 内核 | **6.18.55**（`kernel.release`） |
| `devices` 声明 | `f50 u30air` —— 支持这块板 |
| 模块 | 359 个，装入 `lib/modules/6.18.55/`（与 5.4 并存） |
| OpenWrt | 25.12.5 正常 |
| 5GHz 热点 | ✅ 信道 36 |
| 2.4GHz 热点 | ✅ 信道 6 |
| DHCP / SSH / 外网 | ✅ PC 拿 `192.168.77.232`，`baidu HTTP 200` |

**注意**：`boot_b` 的**内核命令行偏移 44 仍是 `loglevel=5`** —— 这是 Android 侧 `switch.sh` 认
Linux 镜像的依据；`boot_update` 组装新镜像时**沿用原头部**，只改 offset 8/12 的长度字段，所以这个
标记天然保留。**换内核后必须复验一次**，否则会切不进 Linux 且报错指向别处。

## 2. 5GHz 起不来 —— 根因是监管域，不是时序

### 症状

5GHz 配置下 hostapd 直接失败，**设备上没有任何地方报错**：

```
hostapd: wlan0: interface state UNINITIALIZED->COUNTRY_UPDATE
hostapd: Frequency 5180 (primary) not allowed for AP mode, flags: 0x40853 NO-IR
hostapd: Primary frequency not allowed
hostapd: Could not select hw_mode and channel. (-3)
hostapd: wlan0: interface state COUNTRY_UPDATE->DISABLED
hostapd: wlan0: AP-DISABLED
```

### 根因链

```
cfg80211 在 rootfs 挂载前就请求 regulatory.db —— 必然失败
   [2.19s] cfg80211: failed to load regulatory.db
→ cfg80211 停留在世界域 country 00
→ 世界域里 5GHz 全部标记 NO-IR（禁止主动发射）
→ hostapd 不能在该信道起 AP
```

**关键实验**（在同一台设备上）：

```
手动跑 regdb-load 之前： iw reg set TR  → 仍是 country 00      （改不动）
手动跑 regdb-load 之后： iw reg set TR  → country TR: DFS-ETSI  （立刻生效）
                        iw reg set US  → country US: DFS-FCC
                        iw reg set BO  → country BO: DFS-JP
```

所以 `regdb-load`（上游自带，`opt/mu300/bin/regdb-load`）才是关键：它把
`/lib/firmware/regulatory.db` 通过 `/sys/class/firmware` 喂给挂起的固件请求，再 `iw reg reload`。
**开机那次没成功**，于是国家码形同虚设。

### 修法

`mu300-lancheck`（每次开机跑一次）现在**先补喂 `regdb-load`，再修无线**——顺序重要，必须在重启
无线之前，hostapd 才能读到国家码。然后它按 **`operstate` + 是否在网桥里** 判断，不满足就
`wifi down; sleep 3; wifi up`，最多 3 轮。

冷启动实测（6.18 + 5GHz）：

```
hostapd: AP-ENABLED → AP-DISABLED → AP-ENABLED        ← 首次失败
lancheck: 36.79 wlan0 not serving (exists=yes operstate=down bridge-port=1): wifi down; wifi up (attempt 1)
lancheck: 59.87 br-lan=[192.168.77.1/24] ports=[rndis0 wlan0] wlan0=up range=[dhcp-range=...]
```

**两个曾经写错的地方，都值得记一下**：

1. 原来的判断只看「wlan0 是不是网桥端口」。6.18 上 wlan0 **一直在网桥里**，是**射频**起不来，
   所以条件从不触发、日志看着像通过。判据必须是 `operstate`。
2. 第一版修复用 `if [ -d /sys/class/net/wlan0 ]` 守卫整块。但 lancheck 跑的时候 `br-lan` 刚拿到
   地址、**wlan0 还不存在**（lan 接口先于无线接口起来），于是整块被跳过——**在它本该生效的那个场景
   里恰好失效**。必须先等 wlan0 出现（最多 60s）。

## 3. 实体按键：短按切 2.4/5GHz，长按 10 秒重启

### V50 的键码和上游**完全对不上**

`mu300-buttons` 只认 `KEY_POWER=116` 和 `KEY_WIFI=138`（U30 Air 的键）。V50 一个都不报，
所以**按键此前什么都不做**。实测（`/dev/input/event0` 解码）：

| 设备树节点 | `linux,code` | 十进制 | 上游期望 | 说明 |
|---|---|---|---|---|
| `key-power` | `0xBE` | **190** | `KEY_POWER=116` ❌ | KEY_F20 |
| `key-volumedown` | `0x72` | 114 | — | |
| `key-volumeup` | `0x73` | 115 | — | |
| **`key-function`** | `0x1D0` | **464** | `KEY_WIFI=138` ❌ | **KEY_FN，V50 唯一的实体键** |

> 抓取方法：`dd if=/dev/input/event0 bs=24 count=1 | hexdump`，按 `input_event` 结构解
> （64 位下 24 字节：tv_sec 8 + tv_usec 8 + type 2 + code 2 + value 4；`EV_KEY=1`，
> value 1=按下 / 0=释放）。设备上没有 `od`，但有 `hexdump`。

### 改动（`mu300-buttons`）

```sh
KEY_FN=464                      # 新增

# 长按阈值按设备树判断，不按机型：V50 与 F50 的模型字符串相同（DEVICE=f50），
# 但 key-function 这个节点只有 V50 有
HOLD=${MU300_BUTTONS_HOLD:-$([ -d /proc/device-tree/gpio-keys/key-function ] && echo 10000 || echo 3000)}

mu300-keys -l "$HOLD" -t 5      # 原为写死的 -l 3000

case "$code $kind" in
    ...
    "$KEY_FN short") [ "$was_idle" = 1 ] || in_background "$DEADLINE" band_toggle ;;
    "$KEY_FN long")
        logger -t mu300-buttons "V50 key held ${HOLD} ms: rebooting"
        mkdir -p "$PST"; : > "$PST/reboot"
        if is_openwrt; then reboot; else systemctl reboot; fi ;;
esac
```

频段切换直接复用上游的 `mu300-wifi-band toggle`（2g/ch6/HT20 ↔ 5g/ch36/VHT80 + `wifi reload`）。

**实测**：短按 → `band` 从 `2g ch=6` 变 `5g ch=36` ✅；长按 10 秒 → `uptime` 归零、重启 ✅。

> 一个容易误判的点：上游逻辑里「设备处于 idle 时，第一次按下只唤醒、不执行动作」
> （`was_idle`）。所以按键"没反应"时先看 `/run/mu300/power/state` 是否为 `active`、
> `/run/mu300/led/.idle` 是否存在、`mu300-power daemon` 是否在跑——**再**去怀疑键码。

## 4. 无线国家码：选 US（实测功率最高）

`iw reg get` 实测的 EIRP 上限：

| 国家 | 2.4GHz | 5GHz 低段 | 5GHz 高段 |
|---|---|---|---|
| `BO` | 20 dBm | 30（DFS） | 30 |
| **`US`** | **30 dBm** | 23（**允许 AP**） | **30** |
| `CN` | 20 dBm | 23（NO-OUTDOOR） | **33** |
| `TR` / `DE` | 20 dBm | 23 | — |
| `JP` | 20 dBm | 20 | — |

**选 `US`**：2.4GHz 上限 30 dBm，是 BO/CN（20）的 1.5 倍——而 2.4GHz 是唯一在任何监管状态下都能起
AP 的频段；而且 US 允许在低段 5GHz 起 AP（BO 不允许）。

> `CN` 的 33 dBm 只出现在 5.8GHz 段（5725–5850），2.4GHz 仍是 20。
> 注：硬件有自己的发射上限，这几行只是**监管天花板**。

改国家码：`uci set wireless.radio0.country='DE'; uci commit wireless; wifi reload`

## 5. 默认主机名与时区

| 项 | 上游 | 现在 |
|---|---|---|
| 主机名 | （各机型不同） | **`ZTE-V50`** |
| zonename | `Europe/Istanbul` | **`Asia/Shanghai`** |
| timezone | `<+03>-3` | **`CST-8`** |

写在 `openwrt/overlay/etc/uci-defaults/90-mu300`，补丁第 16 步维护。
即时生效：`echo ZTE-V50 > /proc/sys/kernel/hostname`。

### 第 16 步为什么用正则而不是 `Patch()`

第 16 步**曾经**把主机名写成 `V50`。如果照旧用 `Patch()` 去匹配 upstream 的 `mu300`，
在一棵**已经被打过补丁的树**上会 `MISS`——而重跑补丁正是必须支持的场景。所以这里用正则同时接受
`mu300` 和 `V50`，再统一写成 `ZTE-V50`。

## 6. 顺带修掉的顺序 bug：vendor-extra 镜像早了

`apply-v50-patches.ps1` 的镜像步骤（第 7 步）**原本跑在第 10/12/13/16 步之前**，而这几步都会继续改
`openwrt/overlay/` 里的文件。后果：

> 单次干净运行产出的 `openwrt/vendor-extra/` 是**改动前**的内容。
> 而**预编译安装只读 vendor-extra、不读 `openwrt/overlay/`**（那棵树只在 `build-rootfs.sh` 从源码
> 构建时才用）——所以那样的设备会拿到未修补的 `90-mu300` / `10-mu300-usb` / `dashboard-info`，
> 而本仓库看上去是打过补丁的。

重复运行会掩盖它（每次拷贝的是上一次的成品，差一轮）。已改成函数 `Mirror-VendorExtras`，
在第 17b 步（所有内容修改之后、编码门禁之前）调用。

**同类盲区**：`mu300-buttons` 只在 `rootfs/overlay/` 里（`build-rootfs.sh` 把它挂到
`/in/opt-mu300` 再拷进 `/opt/mu300`），**原先不在 vendor-extra 镜像列表里**，同样会漏。
已加入：`opt\mu300\bin\mu300-buttons=rootfs\overlay\opt\mu300\bin\mu300-buttons`。

## 8. 别忘了

- 换内核会**重写 `boot_b`**。动手前先备份它（原有备份脚本只备了 `sml/uboot/trustos/vbmeta/misc`，
  **不含 `boot_b`**）：
  `dd if=/dev/block/mmcblk0p38 of=/data/local/tmp/boot_b.img bs=1M` 再 `adb pull` 出来。
- 换完**复验 `boot_b` 偏移 44 = `loglevel=5`**，否则 `switch.sh` 认不出 Linux 镜像。
- 回退优先级：`mu300-update rollback-boot`（设备内，离线）→ 写回 PC 上的 `boot_b` 备份 →
  BROM 短接刷回。
